## 1. Принципи та правила репозиторію

- **Тільки pnpm**: Заборонено використовувати `npm` або `yarn`. Усі команди встановлення пакетів мають виконуватися виключно через `pnpm`.
- **Повна типізація**: Жодного використання `any` без вагомого коментаря з поясненням. Використовуйте `unknown` або створюйте точні типи/інтерфейси.
- **Дотримання архітектури**: Бекенд організований за модульним принципом, фронтенд — за методологією Feature-Sliced Design (FSD).
- **Хуки перед комітом**: У репозиторії налаштований Husky. Перед створенням коміту автоматично запускаються `oxlint` та `prettier` через `lint-staged`.

## 2. Вимоги до оточення

- **Node.js**: `v22.x` або вище (перевірити: `node -v`)
- **pnpm**: `v10.x` (перевірити: `pnpm -v`)
- **Docker & Docker Compose**: встановлений та запущений Docker daemon

Ініціалізація проєкту:

```bash
# Клонування
git clone https://github.com/viratec-knu/viratec.git
cd viratec

# Налаштування .env
cp .env.example .env

# Встановлення залежностей
pnpm install

# Запуск локальних баз даних
pnpm docker:dev:up

# Генерація типів Prisma
pnpm --filter @viratec/backend db:generate
```

## 3. Робота з гілками (Git Flow)

- `main` — стабільна виробнича гілка. Прямі коміти заборонені.
- `develop` — основна гілка інтеграції.
- Назви робочих гілок повинні мати чіткий префікс:
  - `feat/назва-фічі` — новий функціонал (наприклад, `feat/research-papers-filter`)
  - `fix/опис-бага` — виправлення помилки (наприклад, `fix/auth-token-refresh`)
  - `refactor/назва-модуля` — рефакторинг коду
  - `docs/що-змінено` — оновлення документації
  - `infra/опис` — зміни в CI/CD, Docker або Kubernetes

## 4. Стандарти повідомлень комітів (Commitlint)

Проєкт використовує сувору конвенцію [Conventional Commits](https://www.conventionalcommits.org/). Повідомлення перевіряються автоматично хуком `commit-msg`.

### Формат:

```
<тип>(<скоуп>): <короткий опис>
```

### Дозволені типи (`type`):

- `feat`: Новий функціонал
- `fix`: Виправлення дефекту
- `refactor`: Зміна коду, яка не додає функціоналу і не виправляє баг
- `perf`: Покращення продуктивності
- `style`: Форматування коду, пробіли, крапки з комою
- `docs`: Зміни лише в документації
- `ci`: Зміни в конфігураціях CI/CD
- `chore`: Оновлення залежностей, налаштувань інструментів
- `revert`: Відкат попереднього коміту

### Дозволені скоупи (`scope`):

- `auth`: Авторизація, сесії, права доступу
- `research`: Наукові проекти, лабораторії, публікації
- `projects`: Інноваційні стартапи та розробки
- `events`: Події, конференції, хакатони
- `community`: Форум, пости, коментарі
- `users`: Профілі користувачів, кафедри, факультети
- `infra`: Docker, CI/CD, k8s, моніторинг
- `ui`: Компоненти дизайн-системи
- `backend`: Специфічні зміни серверної частини
- `web`: Специфічні зміни клієнтської частини
- `contracts`: Спільні типи даних та схеми Zod
- `deps`: Оновлення пакетів
- `docs`: Документація

### Приклади валідних комітів:

```bash
feat(research): implement research paper upload with s3 integration
fix(auth): handle expired refresh token gracefully
docs(readme): update quickstart guide for local postgres setup
chore(deps): update fastify and pino packages
```

## 5. Архітектурні стандарти

### Бекенд (Модульна архітектура NestJS)

Кожен бізнес-домен ізольований у власному модулі всередині `apps/backend/src/`:

```
src/
├── research/
│   ├── dto/                    # Data Transfer Objects з валідацією (class-validator / zod)
│   ├── research.controller.ts  # HTTP ендпоінти, декоратори Swagger
│   ├── research.service.ts     # Бізнес-логіка домену
│   ├── research.module.ts      # Nest модуль із реєстрацією провайдерів
│   └── index.ts
```

**Правила:**

1. Контролери не повинні містити бізнес-логіку — лише виклики сервісів та мапінг DTO.
2. Будь-які спільні структури даних переносяться в пакет `packages/contracts`.
3. Усі ендпоінти мають бути задокументовані Swagger-декораторами (`@ApiOperation`, `@ApiResponse`).

### Фронтенд (Feature-Sliced Design - FSD)

Клієнтський додаток в `apps/web/src/` організований строго за рівнями FSD:

1. `app/`: Ініціалізація додатку, глобальні провайдери, стилі, роутер.
2. `pages/`: Композиція сторінок додатку.
3. `widgets/`: Великі самостійні блоки інтерфейсу (Header, Footer, Hero, ProjectGrid).
4. `features/`: Прикладні призначені для користувача сценарії (AuthByEmail, RegisterForEvent).
5. `entities/`: Бізнес-сутності платформи (User, ResearchPaper, Project, Event).
6. `shared/`: Перевикористовуваний UI kit, клієнт API, бібліотечні хелпери, конфіги.

**Правило імпортів:** Шари можуть імпортувати лише модулі з шарів, розташованих **нижче** за ієрархією. Імпорт модулів з того ж шару або шарів вище заборонений.

## 6. Якість коду: Oxlint, Prettier та Knip

Перед відправкою змін обов'язково запустіть валідацію:

```bash
# Швидка перевірка лінтером Oxlint
pnpm lint

# Автоматичне виправлення зауважень лінтера
pnpm lint:fix

# Перевірка форматування
pnpm format:check

# Перевірка типів TypeScript
pnpm typecheck

# Пошук невикористовуваного коду та "мертвих" залежностей
pnpm knip

# Повна валідація одним скриптом
pnpm validate
```

## 7. Робота з Docker

Для локальної розробки достатньо запустити залежні сервіси:

```bash
# Запуск PostgreSQL, Redis та MinIO
pnpm docker:dev:up

# Перегляд логів
pnpm docker:dev:logs

# Зупинка сервісів
pnpm docker:dev:down
```

Для тестування повної продакшн-конфігурації (включаючи збірку образу Nginx та Node.js):

```bash
pnpm docker:prod:up
```

## 8. Процес створення Pull Request (PR)

1. Оновіть вашу гілку актуальними змінами з `develop`:
   ```bash
   git checkout develop
   git pull origin develop
   git checkout your-branch
   git merge develop
   ```
2. Переконайтеся, що всі перевірки проходять успішно: `pnpm validate && pnpm build`.
3. Запуште вашу гілку: `git push origin your-branch`.
4. Створіть PR до гілки `develop`, заповнивши шаблон опису PR.
5. Отримайте апрув від щонайменше одного члена команди після проходження CI/CD перевірок.

Дякуємо за ваш внесок у розвиток інноваційної екосистеми КНУ! 🇺🇦
